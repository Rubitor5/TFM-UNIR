Patrones de Relación

Gestión de Empleados ↔ Gestión de Proyectos

  • Patrón: Cliente-Proveedor (Bilateral)
  • Integración: Tabla de unión compartida (EmpleadoProyecto)
  • Descripción: Los proyectos requieren empleados para asignación. Los empleados rastrean su participación en Proyectos. Los datos están fuertemente acoplados a través de la tabla de unión.
  • Complejidad: Alta - Requiere migración cuidadosa de la base de datos durante la extracción

Gestión de Empleados → Configuración de Aplicación

  • Patrón: Lenguaje Publicado (Unidireccional)
  • Integración: Impulsado por eventos (potencial)
  • Descripción: Los eventos de empleados (creado, modificado, asignado) podrían publicarse para informes/análisis

Gestión de Proyectos → Configuración de Aplicación

  • Patrón: Lenguaje Publicado (Unidireccional)
  • Integración: Impulsado por eventos (potencial)
  • Descripción: Los eventos de proyecto podrían desencadenar instantáneas de informes y monitoreo del sistema

Estrategia de Integración y Patrones

Enfoques de Integración Entre Contextos

1. Proyecto ↔ Empleado (vía EmpleadoProyecto)

Desafío: Transacción entre contextos para asignaciones de Empleado-Proyecto

Patrón Recomendado: Saga (Orquestrado)

  • Enfoque: Cuando un usuario asigna un empleado a un proyecto, una saga coordina ambos servicios
  • Implementación:
    1. ServicioProyecto recibe solicitud de asignación
    2. ServicioProyecto inicia saga, publica evento "AsignacionSolicitada"
    3. ServicioEmpleado escucha, valida disponibilidad de empleado
    4. ServicioEmpleado responde con "EmpleadoAsignado" o "AsignacionRechazada"
    5. ServicioProyecto completa o compensa
  • Manejo de Fallos: Las transacciones compensatorias revierten asignaciones parciales
  • Consistencia: Consistencia eventual (finalización asincrónica)

2. Proyecto/Empleado → Configuración de Aplicación (Informes)

Desafío: Agregación periódica de datos de ambos servicios

Patrón Recomendado: Informes Impulsados por Eventos

  • Enfoque: Los servicios publican eventos de dominio, el servicio de configuración escucha para informes
  • Eventos para Publicar:
    • ProyectoCreado, ProyectoModificado, ProyectoCompletado
    • EmpleadoAsignado, EmpleadoEliminado
  • Implementación: Tópicos Kafka para flujo de eventos, grupos de consumidores para construcción de instantánea
  • Consistencia: Consistencia eventual aceptable para informes

Riesgos Arquitectónicos y Recomendaciones

Riesgos Críticos

🔴 Riesgo 1: Tabla de Unión Compartida EmpleadoProyecto

  • Descripción: EmpleadoProyecto vincula contextos de Empleado y Proyecto, creando acoplamiento transaccional
  • Impacto: Transacciones distribuidas, desafíos de consistencia de datos, implementaciones saga complejas
  • Mitigación:
    1. Implementar orquestación de saga impulsada por eventos para asignaciones
    2. Usar patrón de escritura dual durante migración
    3. Implementar transacciones compensatorias para fallos
    4. Considerar modelo de consistencia eventual
  • Cronograma: Planificar 2 semanas adicionales para diseño y pruebas de saga

🔴 Riesgo 2: Preocupaciones Mixtas en Contexto Usuario/AppInfo

  • Descripción: La gestión de Usuario y AppInfo están agrupadas sin alineación clara de capacidad empresarial
  • Impacto: Cohesión más baja, potencial para preocupaciones transversales futuras
  • Mitigación:
    1. Mantener en monolito por ahora (bajo valor empresarial)
    2. Si se extrae, separar en dos servicios después
    3. Establecer límites claros (Usuario = identidad/auth, AppInfo = versionado/monitoreo)

🟡 Riesgo 3: Complejidad de Migración de Base de Datos

  • Descripción: Migrar de MySQL único a bases de datos múltiples introduce complejidad operativa
  • Impacto: Problemas de consistencia de datos, mayor carga de monitoreo, posible tiempo de inactividad
  • Mitigación:
    1. Usar Liquibase para cambios de esquema versionados
    2. Implementar CDC (Captura de Datos de Cambio) para rastro de auditoría
    3. Planificar pruebas exhaustivas y procedimientos de retroceso
    4. Usar implementaciones azul-verde para migración sin tiempo de inactividad

Riesgos Medios

🟡 Riesgo 4: Latencia de Red en Operaciones Saga

  • Descripción: Las operaciones saga abarcan múltiples servicios, añadiendo latencia de red
  • Mitigación:
    • Establecer tiempos de espera agresivos (5-10 segundos)
    • Implementar disyuntores con Resilience4j
    • Cachear datos frecuentemente accedidos
    • Monitorear latencias P95/P99

🟡 Riesgo 5: Aumento de Complejidad Operativa

  • Descripción: Múltiples servicios aumentan la carga operativa (monitoreo, registro, depuración)
  • Mitigación:
    • Invertir en observabilidad (Prometheus, Grafana, Jaeger)
    • Implementar registro estructurado e IDs de correlación
    • Automatizar implementación con GitOps (ArgoCD, FluxCD)
    • Crear libros de consulta para escenarios comunes
